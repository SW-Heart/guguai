该把智能体做到极致，
还是老老实实做工具台？

读完 shuohao-skills 全部五个 skill 的源码、质量门实现与方法论文档，对照我们现有的 storyboard-engine 与智能导演链路。结论是这个问题问错了对象——智能体和工具台都是驱动方式，真正要建的东西在它们下面。

结论

先建内核：结构化 schema + 确定性质量门 + 提示词编译器，零依赖纯函数，服务端和命令行都能引。这是唯一会长期升值的资产。

再建有界智能体循环：生成 → 校验 → 把违规回灌 → 最多 3 轮。我们现在缺的不是智能体，是校验器驱动的自愈。按实测单价，一轮回修 ¥0.028，三轮不到一毛钱。

工具台不用选——它是内核的第三种驱动，UI 直接读同一套门的结果。而同一个内核打包成 SKILL.md，就是可开源的获客渠道。一套内核，三种驱动，不是二选一。

01

他们到底交付了什么

先破除一个误解：shuohao-skills 里没有一行智能体代码。它交付的是五个自包含目录，每个目录一份 SKILL.md（给智能体读的工作流）加一个零依赖的 Node 脚本（确定性工具），外加 references/ 里的行业方法论。智能体是借来的——用户自己装的 Claude Code 或 codex，用自己的额度跑。

换句话说，他们把最容易被模型迭代冲垮的部分（怎么想）交给了别人，自己牢牢攥住最不容易被冲垮的部分（怎么验）。

四个可以直接抄的机制

  • seed / validate / render / export 四段式 CLI。 seed 把上游事实确定性搬运下来（目标秒数、钩子、爽点、每拍秒数）——已知的事实绝不让模型重想一遍。模型只负责真正创造的那一段，剩下全是代码。这一条直接砍掉大半幻觉面。
  • 每道门都有击穿用例。 selftest 里 outline 200 项、script 137 项、storyboard 165 项断言，不调模型不花额度，每道门都有一个「证明它真的会拦」的反例。我们现在四个测试文件加起来 28 个断言，7 道门没有一道有击穿用例。
  • ⛔ 人类拍板点前置。 大纲写完只出「快版骨架」就停下，把三件事摆给用户拍板：砍了哪条线、合了哪些人、大爆点落第几集。快版错了只损失一轮骨架，分集写完才发现方向错，全废。我们现在是一次出全部再让用户 review 全部——审得太晚、太多、也太假。
  • 体检模式。 用户贴一份现成大纲，只跑门给诊断，不生成。这是一个独立的产品入口，成本几乎为零，却能让没进管线的人先感受到你的专业度。
02

结构上的关键分歧：段 ≠ 镜

这是两边模型最深的一处差异，值得单独讲。

我们的 shot 把三件事压成了一件：一次视频生成、一个连续机位、一个剪辑单元，固定 6 秒。single-take 门因此必须禁止一切切镜。

他们拆成三层：段（一次视频生成调用，≤15 秒，不跨场）→ 分镜（段内 2–5 秒的剪切，认领剧本节拍）→ 分镜图（每切一张关键帧，主图钉 0.00 秒、子图钉各自切点）。一段里可以有 3–5 切，全部由多张参考图控制构图，一次生成出来。

这依赖视频模型支持段内多镜（他们对接 MiniMax H3 的 I2VA 结构）。但真正值钱的不是那个模型细节，是节奏判断：他们的样例平均 3.5 秒一切，方法论里写死「3 秒一切是短剧的呼吸——竖屏观众的注意力就这个粒度」。我们固定 6 秒一镜，比短剧的实际节奏慢了整整一倍。

03

我们缺的门，按值钱程度排序

我们那 7 道门全是工程门——覆盖、时长、单镜、引用、衔接、顺序、运动轴。它们保证「拍得出来」，一道也不保证「有人看」。下面是缺口清单，前六条是内容门，后三条是工程门。

钩子前 3 拍内兑现缺失

每集第一拍冷开场必须给出钩子的具象——皮箱特写、口袋里方硬的轮廓。hookBeat 认领具体位置，门查它是否落在前 3 拍内。

短剧的生死线在前 3 秒。这是投入产出比最高的一道门，也是我们完全没有的一层。

爽点间隔 ≤ 3 集无真空缺失

爽点分布上门：开头不能空、中间不能断档、结尾不能真空，大爆点不许压到最后一集才首次出现。

这是把「节奏」变成可计算量的唯一办法。落到我们的单集尺度就是：反转间隔 ≤ N 秒。

常见动作判据缺失

动作节拍只写 AI 见过千万次的动作。挑担上船、搭手卸担 ✓；伸篙一挡、睫毛颤、退了半寸 ✗。

我们的 ABSTRACT_ACTION 只用 $ 锚定结尾拦「充满张力」，「充满张力地转身」照样放行。他们把它升级成了一条有判据的规则：精确物理交互、微表情、以寸计的位移、比喻性画面——全拦。

每场至少一个动作节拍缺失

三句台词之间没有一个画面动作，这场戏就是广播剧——AI 生成时没有画面可写。

一行代码的门，直接拦掉一整类不可生成的场次。

单句台词 ≤ 35 字缺失

一口气说得完。长句拆两句，中间插一拍动作或对方反应。

直接决定 TTS 和口型的可用性，也是「演讲癖」的机械解药。

同框 ≤ 3 人，超了要带拆解缺失

三人以上同框必须写清调度方案：谁在前景说话、谁在背景反应。

多人同框是当前视频模型最稳定的崩坏源。写在纸面上比生成完再返修便宜两个数量级。

生成难点关键词预警缺失

正则扫描梗概，命中雨戏 / 肢体接触 / 人群 / 手部特写就要求显式登记进预警清单。宁可多报。

十几行代码，把「事后发现生成不了」提前到剧本阶段。

集级时长预算 ±15%缺失

我们只有单镜 ±0.35 秒，没有「一集三分钟就是三分钟」这一层。

缺了它，单镜每个都合格、整集长度失控。

已有的 7 道工程门保留

覆盖 / 时长 / 单镜 / 引用 / 衔接 / 顺序 / 运动轴。方向正确，只是正则实现偏脆，且没有击穿用例。

不用推翻，补测试 + 收紧匹配即可。

04

回到抉择本身

你问的是「把智能体能力发挥到极致，还是不做智能体只做工具台」。把两边推到极端看会更清楚。

选项 A

纯工具台

用户手工填完场次、节拍、资源圣经、每镜逐秒运动轴。系统只负责校验、编译、生成、拼接。

问题是：我们已经有工具台了——「专业编辑」模式就是。它没有成为差异化，因为让人手填 50 个字段的产品没有人用。工具台是必要的兜底，不是产品主张。

建设成本 低 · 差异化 无 · 已验证不成立

选项 B

极致智能体

策划 / 编剧 / 美术 / 分镜四个智能体，各带工具，自主协作，跑几分钟出全套。

问题是：没有验证器的智能体，多跑几轮只会产出更自信的垃圾。模型无法自评「这个钩子够不够狠」，它只会说够。轮数增加的是信心，不是质量。

建设成本 高 · 无门时质量不收敛

建议 · 选项 C

内核 + 三驱动

内核 = schema + 质量门 + seed + 编译器 + render，零依赖纯函数。三种驱动共用它：产品内有界智能体循环、工具台 UI（实时亮灯）、开源 SKILL.md 包（给 Claude Code / codex 用户）。

智能体不是产品，是内核的一种驱动。工具台也是。开源包还是。三者同时存在，成本只多一份内核。

建设成本 中 · 三条分发路径共用一份资产

为什么顺序必须是「先门后智能体」

这是整份备忘里我最想让你记住的一句：质量门是智能体的前提，不是智能体的替代品。

有门无智能体，用户自己按报错手改，体验差但质量收敛。有智能体无门，模型自由发挥，体验顺滑但质量随机漂移——而且你无法知道它漂了。两者都有，智能体才第一次拥有了「知道自己错在哪」的能力，回修才成立。

我们现在的状态是第三种：有门，但门只会杀死结果。assertProductionPlan 抛错、退积分、让用户重来。门的价值被浪费了 90%——它已经精确算出了违规清单，却只用来判死刑，不用来指导重写。

成本这一关已经过了。实测账单：一次智能导演调用输入 1686 token、输出 3898 token，计费 0.28 积分 = ¥0.028。三轮回修 ¥0.09，十轮 ¥0.3。成本根本不是拦路虎——拦路虎是同步 HTTP 请求撑不住多轮循环。而这个也已经有现成解法：/api/generations 早就是 202 + 轮询 的异步模式（startGeneration + activeGenerations），智能导演接口照抄即可。
05

落地路线

严格按依赖排序。每一阶段都独立可交付，不做完不进下一阶段。

  1. 阶段 0约 1 周

    内核化与击穿用例

    把 storyboard-engine.mjs 提成独立 kernel/，零依赖纯函数，服务端与命令行同源引用。同时补测试。

    • 现有 7 道门，每道至少一个击穿用例，证明它真的会拦
    • 收紧 ABSTRACT_ACTION（去掉 $ 锚定）与 CUT_WORDS（避免误杀台词里的「切到」）
    • 删掉 video-prompt.js 里四个从未调用的死函数
    • 资源图提示词改为服务端重新编译，与视频侧对齐
    交付：门可信，且可被两种驱动复用
  2. 阶段 1约 2 周

    有界回修循环 + 异步化

    这一步不加任何新门，只让现有的门从「判死刑」变成「开药方」。这是当前投入产出比最高的改动。

    • /direct 改成 202 + 轮询，复用 startGeneration 模式
    • 生成 → storyboardGateReport → 把 gate.problems 连同原方案回灌 → 重出，最多 3 轮
    • 积分预留按 3 轮上限冻结，实际按轮次结算
    • 前端展示每轮修了什么——这个过程本身就是专业感
    • 顺手解决 shots.length 必须严格等于 shotCount 的硬失败：改成回修目标而非致命错误
    交付：失败率从「一次不过就废」降到「三轮内自愈」
  3. 阶段 2约 3 周

    内容门与分层拍板

    把一次性出全包拆成四次调用，每层之间插一个 ⛔ 人类拍板点，同时按 §03 的清单补内容门。

    • 拆层：策划（题材/爽点表/分集）→ 剧本（场次/节拍/台词）→ 美术（资源圣经）→ 分镜（段/切/运动轴）
    • 每层 seed 上游事实，模型只写该层真正新增的内容——同时根治 12000 token 截断问题
    • 拍板点只摆三件事，不让用户 review 全部
    • 内容门按 §03 顺序上：钩子 → 反转间隔 → 常见动作 → 每场动作 → 台词长度 → 同框人数 → 难点预警 → 集级时长
    交付：从「格式化分镜生成器」变成「导演」
  4. 阶段 3待模型能力确认

    剪辑粒度与段内多镜

    先做无依赖的那一半：把固定 6 秒改成可变 2–8 秒，让节奏能快起来。段内多镜取决于视频模型是否支持多帧对齐，需要先做能力测试再决定。

    • 无条件可做：单镜时长可变、深浅长短相间的节奏带、正反打 / 插入特写 / 反应镜头的切镜语法进 prompt
    • 有条件才做：段（≤15 秒，多切）作为一次生成单元，多张关键帧控制构图
    交付：节奏对上短剧的呼吸
  5. 阶段 4机会窗口

    开源 skill 包与体检入口

    内核已经是零依赖纯函数，打包成 SKILL.md + scripts/ 几乎零边际成本。

    • 开源包做口碑与获客；托管产品做他们做不了的那半边——图像与视频生成我们自己接，用户不需要装 codex
    • 体检模式作为独立入口：贴一份现成剧本或分镜，只跑门给诊断报告，不生成、不收费
    交付：一份内核，两条分发路径
06

不要照抄的部分

  • 小说长文本的分卷 map-reduce。 他们的输入是整本小说（80 万字级），需要 chunk 按章节分卷再逐卷摘要。我们的输入是一句话创意或单集剧本，这整套脚手架不需要。
  • H3 提示词逐字对账。 把对齐指令和切点时刻绑死到一个特定视频模型，我们是多模型路由（grok-video-1.5 / veo3.1-fast），照抄会立刻被模型更换打穿。要抄的是「秒数改了提示词必须同步改，且由代码对账」这个原则，不是那份格式。
  • 无限子代理并发。 他们在用户自己的额度里跑，可以「同一条消息里全部发出」。我们是多租户计费系统，必须是受控并发 + 配额 + 预留结算。
  • 零 API key 的前提。 他们能这么设计是因为智能体是借来的。我们的智能体是自己掏钱的，所以「有界」两个字必须刻在循环里。
唯一的真实风险：门和回修必须同批上线。只加门不加回修，等于把失败率直接抬到用户脸上——现在 7 道门就已经会让一次生成整包报废，加到 15 道会让通过率跌到不可用。阶段 1 必须先于阶段 2，这个顺序不能调换。另外 deepseek-v4-flash 大概率扛不住十几道门的结构化生成，建议分级：结构生成用强模型，格式修补用便宜模型；同时把 outputSchema 存在时强制 thinking:'disabled' 这条改掉——分镜恰恰是最需要推理的任务。

研究材料：eternityspring/shuohao-skills（Apache-2.0，五个 skill 的 SKILL.md、references、scripts 与 selftest 全部通读）；Anthropic Agent Skills 官方规范（SKILL.md 格式、渐进式披露、bundled scripts 与 references 的加载模型）。
